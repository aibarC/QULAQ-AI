# QULAQ2 — согласованный процесс CQA

Зафиксировано 7 ноября 2026 по запросу пользователя после повторного чтения ТЗ и независимой проверки двумя субагентами. Это спецификация процесса, а не отчёт о реализованном приложении. Разработка приложения ещё не начата.

## Источники и границы

- `CQA_Hackathon_Student_Guide_v3 1.pdf`: требования к функциям, API, ролям и сдаче.
- `CQA_Chat_Quality_Checklist 1.pdf`: критерии и правила расчёта.
- Оба исходных PDF находятся в `/Users/srkaibar/Downloads/Telegram Desktop/` на исходном компьютере; этот путь не является зависимостью приложения.
- DEV API проверен в этой сессии: 65 разговоров, 60 чатов и 5 звонков; 35 RU, 15 KZ, 15 EN. Поля записи: `conversation_id`, `channel`, `language`, `transcript`, `audio_url`. Транскрипт — массив реплик с `timestamp`, `speaker`, `text`. Аудиоссылки присутствуют у пяти звонков. Отдельного поля имени сотрудника нет.
- Секретную подписанную ссылку API не публиковать в репозитории.
- Названия экранов, кнопок, статусов и организация хранения ниже — согласованные решения для реализации требований, а не буквальный макет организаторов.

## 1. Роли по ТЗ

| Участник | Действия |
|---|---|
| Пользователь приложения | Загружает диалоги, настраивает чек-лист, запускает оценку, смотрит результат и оспаривает критерий. |
| Проверяющий | Рассматривает обращение, проверяет доказательства, подтверждает или меняет оценку с причиной. |
| Оператор внутри разговора | Объект оценки; не обязательно пользователь приложения. |
| ИИ | Выполняет первоначальную оценку и приводит доказательства. |

Нельзя сводить процесс к одному руководителю или утверждать, что пользователь обязательно оценивает собственные записи. Должности и владение разговорами не установлены ТЗ. Есть две человеческие функциональные роли, но два аккаунта не требуются: для демонстрации подача и рассмотрение — отдельные действия без регистрации.

Для нашего продуктового сценария согласовано: пользователь — специалист контроля качества, который работает с разговорами других операторов; проверяющий — второй специалист, разрешающий спорные случаи. Оператору из записи доступ к приложению не требуется. Это выбранный сценарий, а не установленная организаторами должность.

## 2. Интерфейс

Одно приложение с переключателем **Пользователь / Проверяющий** для демонстрации. Он не является системой авторизации. Интерфейс дорабатывается итеративно, но роли и полный путь должны сохраняться.

Режим пользователя:
- **Диалоги**: импорт, список разговоров, карточки и результаты.
- **Чек-листы**: редактирование и сохранение правил.
- **Мои апелляции**: отправленные обращения, статусы и решения проверяющего. В демо это обращения одного демонстрационного пользователя; настоящая идентификация не реализуется.

Режим проверяющего:
- Только **Апелляции**: общая очередь и история рассмотрения.
- Внутри обращения доступны полный разговор, аудио, исходный критерий, оценка и форма решения. Отдельные разделы всех диалогов и редактирования чек-листов ему не нужны.

## 3. Полный путь

### Шаг 1. Импорт набора

На первом экране пользователь видит поле набора с `DEV` и кнопку **Загрузить набор**. Сервер получает данные через GET API с `group_id`. Все разговоры набора появляются в списке со статусом **Не оценён**.

Колонки списка: ID разговора, канал, язык, состояние оценки, итог; количество открытых апелляций при их наличии. Не показывать вымышленные имена или рейтинги сотрудников.

Импорт набора и оценка — отдельные действия. Загрузка отдельных аудиофайлов и транскрибация не нужны: текст уже предоставлен. У чатов время MM:SS, у звонков ISO 8601 с часовым поясом; исходные метки сохраняются.

### Шаг 2. Чек-лист

Начальная конфигурация — восемь критериев из PDF. Пользователь может добавлять и менять критерии, формулировки, веса, тип ответа, разрешение и условия N/A, числовые шкалы. Нажимает **Сохранить чек-лист**. Конфигурация повторно используется для разных разговоров.

Сохранение конфигурации не запускает анализ автоматически и не переписывает старые результаты. Новый критерий должен реально применяться через настройки без изменения кода.

### Шаг 3. Оценка выбранного разговора

Пользователь открывает строку списка. В карточке слева транскрипт с ролями и временем, для звонка также плеер или ссылка на запись; справа выбор чек-листа и кнопка **Оценить**.

Система передаёт модели транскрипт и правила, получает ответы, объяснения и ссылки на доказательства, проверяет допустимость результата, рассчитывает баллы кодом и сохраняет результат.

Оценивается оператор. Роли client, bot и system используются как контекст. Поддерживаются RU, KZ и EN. Массовая оценка — полезное дополнение, но обязательный путь — оценка выбранного диалога.

### Шаг 4. Просмотр результата

Показываются общий итог, результаты секций если они заданы, ответ/балл и вес каждого критерия, объяснение и доказательство. Для N/A показывается причина, для пропущенного действия — проверенный участок. Грубые нарушения отмечаются отдельно.

Ошибки и потерянные баллы можно ставить первыми; успешные критерии тоже доступны. Ссылка открывает нужную реплику или фрагмент разговора. Для звонка доступно прослушивание или переход к плееру. Точность привязки аудио к меткам необходимо проверить на данных до обещания точного перехода.

Если пользователь согласен, он возвращается к списку. Подтверждать каждый критерий не требуется. Результат остаётся сохранённым, разговор — в списке со статусом **Оценён**.

### Шаг 5. Подача апелляции

Возле конкретного критерия пользователь нажимает **Оспорить**, пишет комментарий и нажимает **Отправить апелляцию**.

Обращение сохраняется в общем хранилище приложения и связывается с конкретным разговором, результатом и критерием. В исходной карточке появляется статус ожидания и ссылка на обращение. Оно видно пользователю в **Моих апелляциях**, а проверяющему — в очереди **Апелляции**.

Комментарий сам по себе не меняет баллы, не отправляется автоматически модели и не запускает повторные циклы оценки.

### Шаг 6. Рассмотрение

Проверяющий открывает режим **Проверяющий**, раздел **Апелляции** и обращение из общей очереди. Назначение конкретному сотруднику и внешние уведомления для основы не нужны.

Проверяющий видит исходное правило, оценку и объяснение ИИ, комментарий пользователя, транскрипт и доказательства, аудио при наличии.

Форма решения:

- **Подтвердить исходную оценку**, либо
- **Изменить оценку** и выбрать допустимый ответ/балл;
- обязательная причина;
- **Сохранить решение**.

Одного тега или комментария недостаточно: эта форма и сохранение решения обязательны.

### Шаг 7. Решение и пересчёт

Если исходная оценка подтверждена, балл не меняется. Если ответ критерия изменён, код пересчитывает общий итог. Человек выбирает только значения, разрешённые шкалой; N/A — только при разрешении и выполнении условия.

Сохраняются исходная оценка ИИ, обращение, решение с причиной и итог после пересмотра. Сам текст причины не преобразуется в баллы моделью. Повторный запуск ИИ не требуется.

### Шаг 8. Возврат результата пользователю

В той же карточке пользователь видит исходную оценку, решение проверяющего, причину и текущий итог. Разговор остаётся в списке, рассмотренное обращение — в истории апелляций. Ничего автоматически не исчезает.

Несколько спорных критериев рассматриваются отдельно. Пока есть открытые обращения, показывается их количество; весь процесс не обозначается завершённым.

## 4. Статусы

Предлагаемые состояния оценки: **Не оценён / Оценивается / Оценён / Ошибка оценки**. Отдельно показываются открытые апелляции и факт пересмотра человеком. У обращения: **Ожидает рассмотрения / Рассмотрено**, с решением оставить или изменить оценку.

Это названия интерфейса, а не предписанные ТЗ значения. Апелляция обязательна как функция, но не как этап каждого разговора.

## 5. Расчёт

Начальные критерии: контакт 10; выявление потребности 15; идентификация 20; консультация 20; эмпатия 15; ведение диалога 15; завершение 5; грубые ошибки — отдельный флаг без баллов.

- Да = полный вес, Нет = 0.
- Консультация: 0, 5, 10, 15, 20; ведение диалога: 0, 4, 7, 10.
- Балл шкального критерия = вес × оценка / максимум шкалы.
- Итог = 100 × сумма взвешенных баллов / сумма весов применимых критериев.
- N/A исключается из числителя и знаменателя; это не штраф и не неопределённость модели.
- Итог округляется до двух знаков. Если применимых весовых критериев нет, итог не рассчитывается.
- Грубая ошибка не обнуляет результат по выданным правилам.
- Порог первой реакции 3 минуты, теги и вложения исключены из оценки.

## 6. Повторная оценка и изменение правил

Каждый новый запуск создаёт отдельный результат со снимком/версией использованных правил. Старое обращение остаётся привязано к старому результату. Новая оценка не затирает решение человека. Это инженерное решение для воспроизводимости и отсутствия тупиков.

Изменение формулировки требует новой проверки по новому правилу. Если изменился только вес, арифметический пересчёт возможен без обращения к модели, но также не должен незаметно переписывать исторический результат.

## 7. Обработка ошибок и сохранение

| Ситуация | Поведение |
|---|---|
| Ошибка API | Сообщение и повтор, уже загруженные разговоры сохраняются. |
| Ошибка ИИ или недопустимый ответ | Ошибка оценки и повторный запуск; не изображать нулевой балл как успешный результат. |
| Обновление страницы | Сохранённые чек-листы, результаты и обращения доступны. |
| Повторная подача на тот же критерий того же результата | Открыть существующее незавершённое обращение, не создавать дубль. |
| Правила изменены во время спора | Показывать правила исходной спорной оценки. |
| Решение не сохранилось | Не показывать успешное завершение обращения. |
| Аудио недоступно | Показать недоступность/ссылку, сохранить доступ к транскрипту. |

## 8. Контрольный набор

Через 23 часа после старта организаторы открывают контрольные транскрипты и сообщают другой `group_id`. Через ту же форму импорта загружаем набор, получаем новые строки и оцениваем выбранным чек-листом. Прямой доступ к внутренней БД организаторов не нужен.

Через 24 часа — стоп-код. На зафиксированной версии разрешены обработка данных и изменение чек-листа через интерфейс. На отдельной проверке необходимо заменить предложенный критерий через настройки и применить его.

## 9. Граница основной версии

Обязательно: импорт готовых разговоров, редактируемый чек-лист, оценка, доказательства, корректный расчёт, подача апелляции, человеческое рассмотрение, пересчёт и сохранение исходного и финального результатов.

Не требуется для основы: STT, обучение собственной модели, автоматическое обучение на апелляциях, повторные запросы к ИИ до согласия пользователя, регистрация, персональные кабинеты и рейтинги сотрудников, уведомления.

Исправление оценки человеком не обучает модель. Опциональный Auto Improve AI описан отдельно в [OPTIONAL_FEATURES.md](OPTIONAL_FEATURES.md) и не входит в этот основной процесс.

Не определены документами: должности ролей, владение записями, точная формула секционных итогов, отдельный голосовой чек-лист, база фактов для проверки консультаций, смешение языков внутри звонков. Эти пробелы не выдавать за подтверждённые требования.
