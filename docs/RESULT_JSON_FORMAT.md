# JSON результата QULAQ · версия 1

В интерфейсе доступны два разных JSON-экспорта. XLSX-кнопки убраны.

## Официальный JSON всего набора

На странице диалогов блок «Результаты для организаторов · JSON 1.0» выгружает весь выбранный набор, независимо от фильтров. Выберите группу, DEV (65 диалогов) или контрольный набор (10), укажите команду (по умолчанию Amazing Guys). Запрос `POST /api/exports/submission` с `groupId`, `teamName`, `expectedCount` возвращает официальный документ без вызова модели. Сохраните скачанный `results.json` в `results/dev/results.json` или `results/prod/results.json`.

Формат задан приложением организаторов: `schema_version: "1.0"`, `team_name`, `model`, `results[]`. Коды: contact, discovery, identification, consultation, empathy, dialogue, closure, critical. `evidence_turns` нумерует исходный transcript с 1, включая клиента, бота и события. Ошибки обработки имеют status=error, criteria=[], score=null и error. Сервер проверяет количество, уникальность ID и совместимость с исходным восьмикритериальным чек-листом; пользовательские правила нельзя незаметно выдавать за стандартную сдачу. При отказе показывается ошибка, файл не скачивается.

## Подробный JSON одного диалога

Кнопка «Скачать JSON этого диалога» в карточке сохраняет внутренний подробный формат приложения `format: "qulaq.evaluation"`, `schema_version: 1`. Он содержит историю, транскрипт и дополнительные данные и **не заменяет официальный файл всего набора**.

| Поле | Значение |
|---|---|
| `conversation_id` | Исходный `conversation_id` организаторов, без хеша и внутреннего префикса |
| `dataset_group_id` | Исходная группа набора, например CONTROL |
| `evaluation_id`, `created_at` | ID и время выбранного анализа |
| `source_kind` | server, demo или preview — учебный/Excel-результат не маскируется под серверный |
| `language`, `channel` | Язык и канал разговора |
| `checklist` | Полный снимок правил и версии выбранного запуска |
| `original_total`, `total`, `gross_violation` | Исходный и текущий итог, отдельный флаг грубого нарушения |
| `results` | Все критерии из снимка, в порядке чек-листа |
| `transcript` | Реплики: message_id, исходный timestamp, speaker, text |
| `provenance`, `contact_reason`, `classification_error`, `conversation_improvement` | Сохранённые дополнительные данные, если присутствуют |

Каждый элемент `results`: `criterion_id`, `criterion_name`, `criterion_type`, `rule_description`, `status` (scored/not_applicable), `value`, `original_value`, `weight`, `points`, `reason`, `original_reason`, `evidence`. Для N/A `value` и `points` остаются JSON null, условие объясняется в `na_reason`. При пересмотре `reason` — причина проверяющего, исходное объяснение сохранено отдельно; `review` содержит value/reason/appeal_id. Необязательный `coaching` сохраняет совет по критерию.

`evidence` содержит kind/message_ids/quote. Все message_ids разрешаются через `transcript[].message_id`; это внутренние стабильные ID реплик, поскольку исходный формат организаторов не задаёт им отдельного ID. Поля времени сохраняются без замены на экранный относительный отсчёт.

Перед созданием JSON проверяются сохранённая схема, соответствие разговору, полный состав критериев, допустимые ответы и ссылки на реплики. Итоги берутся из сохранённого анализа, не вычисляются заново при скачивании. Экспорт не вызывает модель.

В файл не входят API-ссылка, аудиоссылки с возможной подписью, токены или остальные разговоры Workspace. Сам транскрипт входит: файл предназначен для осознанной передачи результата пользователем.

## Сохранение ID при импорте

Официальный JSON-файл и импорт по API сохраняют `dataset_group_id` и `conversation_id`. Внутри приложения запись имеет ID вида `GROUP:encoded-conversation-id`, чтобы разные наборы не конфликтовали; внешний ID не изменяется и отдельно экспортируется. Повторный идентичный импорт не дублирует запись, изменение содержимого под тем же ID не перезаписывает историю.

TXT/PDF не имеют официальных полей ID, поэтому для них сохраняется группа UPLOAD и генерируется устойчивый ID из содержимого/имени файла. Старые ранее импортированные записи с хешированным ID автоматически не переименовываются: это могло бы нарушить связь с оценками и апелляциями.
