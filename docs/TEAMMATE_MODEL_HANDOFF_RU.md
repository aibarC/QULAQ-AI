# Передача разработки моделей — QULAQ-AI

Состояние на 8 ноября 2026. Актуальная ветка: `codex/frontend-manager-report`. Это дополнение к корневому README, а не инструкция запускать оплачиваемые запросы без разрешения.

## Что делать напарнику в первую очередь

**Главная задача — качество ответа Kimi, особенно конкретных советов оператору. UI, JSON-поля, проверка, хранение и отображение уже сделаны.** Отдельную генеративную модель для советов не добавляли: Kimi выдаёт их в том же ответе, что и оценки. Изменение prompt не означает обучение весов модели.

1. Проверить `backend/src/prompt.ts` и форму ответа ниже. Сохранить строгую схему и совместимость старых результатов.
2. Подготовить небольшую вручную проверенную выборку RU/KZ/EN: верное обслуживание, явные ошибки, недостаток бизнес-контекста, смешанная речь, неясная расшифровка. Разделить разработческую и контрольную части.
3. Для каждого нарушения проверить три вещи: оценка верна; evidence действительно подтверждает её; предложенная реплика полезна именно в этом месте и не выдумывает условия компании.
4. Сопоставить советы с утверждёнными правилами компании. Если правил нет, нужен `needsContext=true`, а не правдоподобный вымысел.
5. Только после отдельного разрешения выполнить согласованный реальный тест. Сохранить model/prompt version, время, токены, ошибки формата и ручную оценку. Число токенов не равно стоимости без тарифа шлюза.
6. После улучшения повторить тесты и описать изменения. Не менять веса/формулу оценки ради улучшения метрик prompt.

## Ответ Kimi

Модель возвращает JSON с `results` и `contact_reason`. По одному результату на каждый критерий; никакого вычисления total/points моделью. Числа рассчитывает `scoring.ts`.

Синтетический пример одного нарушенного критерия (полный массив должен включать все критерии переданного чек-листа):

```json
{
  "criterion_id": "c2",
  "status": "scored",
  "value": false,
  "reason": "Оператор не уточнил, на каком шаге клиент столкнулся с проблемой.",
  "evidence_ids": ["example:m3", "example:m4"],
  "evidence_kind": "messages",
  "coaching": {
    "response": "Подскажите, на каком шаге возникает затруднение и какое сообщение вы видите?",
    "explanation": "Уточнение собирает недостающие сведения перед рекомендацией и выполняет правило выявления потребности.",
    "needsContext": false,
    "messageIds": ["example:m3", "example:m4"]
  }
}
```

Точные реальные ID берутся из переданного транскрипта; `example:*` выше — только иллюстрация.

### Правила coaching

- Только для исходного нарушения: boolean=false, scale ниже максимума, flag=true. Для выполненного/N/A — null или отсутствие поля.
- Реплика на языке клиента, 1–3 предложения; объяснение по-русски, 1–2 предложения, связь с конкретным правилом. Лимит каждой строки — 2000 символов.
- Не выдумывать тарифы, сроки, обещания возврата, успешную идентификацию или выполненную операцию.
- Если безопасная реплика без внешнего правила невозможна: `response=null`, `needsContext=true`, explanation объясняет, какого контекста не хватает. Безопасный уточняющий вопрос допустим, если он действительно исправляет нарушение.
- `messageIds`: 1–100 уникальных ID того же разговора. Это основание совета, не новая реплика в транскрипте.
- При апелляции исходный совет сохраняется; UI скрывает его, если текущий ответ уже не является нарушением. Старые записи без coaching открываются без искусственного совета.
- Отсутствие coaching у старого/совместимого ответа не ломает оценку. Напарнику нужно отдельно измерять, насколько часто новая модель пропускает обязательный совет.

### Причины и исходы

`contact_reason` содержит `taxonomyVersion`, `primary`, `secondary`, `summary`, `reason`, `evidenceIds`, `resolution`. Точные ID категорий в `frontend/src/lib/contactReasons.ts`. Исход `resolved|unresolved|unknown` подтверждается репликами; вежливое прощание не доказывает решение. Не возвращать `classifier`: источник Laya может назначить только сервер.

При подключённой Laya Kimi-категория пока заменяется локальной. Оптимизация для следующей итерации: согласованно убрать дублирующий выбор категории из prompt Kimi, сохранив анализ исхода и совместимость схемы. Это **ещё не реализовано**; не удалять поле из ответа без изменения scorer/тестов.

## Laya: что нужно улучшить

Реализовано: после scoring автоматически берутся evidence критерия `c2` с названием «Выявление потребности» и соседние ±1 реплики; локальный worker выбирает одну из девяти групп. Сохранены model/revision и ID фрагмента. Нет фрагмента/слишком длинный/ошибка worker — сохраняем оценку Kimi с явной ошибкой классификации. Для старых оценок есть отдельный endpoint и кнопка.

Нужны ручная разметка, проверка полноты фрагмента, отдельная оценка RU/KZ/EN и смешанной речи. Нельзя доверять raw probabilities как готовой уверенности: checkpoint не откалиброван под наши категории. Проверка 5/6 на простых примерах и спорный реальный выбор показывают необходимость работы над качеством. Возможные дальнейшие шаги — улучшение схемы фрагмента/описаний, дообучение на размеченных примерах или сравнение с альтернативой. Ни один из них пока не заявлен выполненным.

При смене основной темы прежний resolution становится unknown, чтобы не переносить «решено» на другую потребность. Не восстанавливать прежний Kimi-primary скрыто под источником Laya. Установка/ограничения: [backend/laya/README.md](../backend/laya/README.md).

## Карта реализации

| Файл | Назначение |
|---|---|
| `backend/src/prompt.ts` | Инструкции Kimi: критерии, evidence, coaching, причины/исходы |
| `backend/src/provider.ts` | Шлюз Kimi, одноразовый gate, затем локальная классификация |
| `backend/src/scoring.ts` | Проверка ответов, расчёт баллов, пересмотр |
| `backend/src/laya.ts` | Извлечение фрагмента, безопасный worker, provenance и ошибки |
| `backend/laya/classify.py` | Offline inference закреплённой Laya Multilingual |
| `backend/src/server.ts`, `store.ts` | HTTP, апелляции, локальное хранение |
| `frontend/src/lib/types.ts`, `validation.ts` | Общий контракт и проверка целостности |
| `frontend/src/components/CoachingAdvice.tsx` | Совет в результате, апелляции и отчёте |
| `frontend/src/components/ManagerDashboard.tsx`, `ManagerTrend.tsx` | Отчёт, график, доказательства |
| `frontend/src/components/ContactReasonsPanel.tsx` | Группы, поиск, исходы и локальная классификация |

## Не путать проверки с качеством модели

Unit/HTTP/browser tests подтверждают форматы, вычисления, сохранение, переходы, сбои и отсутствие лишних запросов. Они не доказывают правильность живых советов или категорий. Два старых запуска Kimi были до coaching; новый формат ещё нужно проверить с реальной моделью по отдельному разрешению. Токен агенту читать нельзя. Реальные транскрипты и аудио в Git не переносить.
