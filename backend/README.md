# Локальная связка MVP

Node.js 24+, TypeScript. Сервер слушает только `127.0.0.1:8000`, хранит Workspace в `.local/server/workspace.json` и предоставляет API существующему frontend. Это локальный MVP без многопользовательской авторизации, не готовое публичное размещение.

## Запуск всей связки

Из корня репозитория:

```sh
npm run setup
npm run dev
```

Открыть http://127.0.0.1:5173. Порты 5173 и 8000 должны быть свободны. Команда поднимает сервер и Vite с проксированием `/api`; остановка завершает оба процесса. Серверные и frontend-зависимости устанавливаются отдельно, root-пакет не содержит зависимостей.

Для исходных 65 диалогов требуется приватный `dev.json` в корне. Он передаётся отдельно и не включается в Git. Без него можно загрузить собственный транскрипт через интерфейс. Данные, результаты и апелляции хранятся локально и восстанавливаются после перезапуска; незавершённый анализ получает ошибку и никогда не перезапускает модель автоматически.

## Состояние модели и секреты

Обычный запуск включает ручной режим: открытие приложения не вызывает модель и не читает `.env`, но кнопки анализа и улучшения могут выполнить реальные запросы. Нет автоматических повторов. Для отключения вызовов запускайте backend с `--disable-llm`; `--allow-one-llm-request` оставлен для отдельно разрешённого одноразового теста. Одна такая квота общая для анализа и улучшения.

Сервер использует `LLM_BASE_URL` и `LLM_API_TOKEN` из корневого `.env` только при ручном действии модели. Пользователь вводит токен самостоятельно. Агентам запрещено читать файл, выводить токен, окружение или заголовки. Frontend секрет не получает. Агент не запускает платные тесты без отдельного разрешения пользователя и не удаляет квитанции использованных запросов. Текущая модель по умолчанию — `kimi-k3`; настройки в `src/config.ts`.

## Пользовательский путь

1. Пользователь вставляет HTTPS-ссылку API организаторов либо выбирает PDF/TXT/JSON. В API-режиме автоматический импорт DEV отключён.
2. «Открыть для анализа» сохраняет импорт на локальном сервере и открывает карточку. Загрузка не вызывает модель.
3. TXT должен явно содержать роли, например `Клиент: Вопрос` и `Оператор: Ответ`; время `[00:03]` необязательно. Без роли первая реплика не принимается для анализа. JSON использует формат DEV. Аудиоссылки официального JSON сохраняются для плеера, но сервер не скачивает их автоматически.
4. «Оценить» создаёт серверную задачу в ручном режиме; при `--disable-llm` возвращается явный отказ. Frontend показывает ожидание и опрашивает Workspace.
5. Подтверждённый новый результат открывается в той же карточке: снимок чек-листа, баллы, пояснения, ссылки на реплики и скачивание подробного JSON диалога. Итогов до анализа в списке нет. Старый результат не подтверждает новый запуск.
6. Апелляция сохраняется на сервере; решение меняет финальную оценку, сохраняя исходные ответы и итог.

## Контракт

Все успешные операции возвращают полный Workspace, который проверяется существующим клиентским валидатором.

| Метод | Путь                        | Данные                                           |
| ----- | --------------------------- | ------------------------------------------------ |
| GET   | `/api/workspace`            | —                                                |
| POST  | `/api/datasets/import-url` | `{url, groupId?}`; HTTPS GET, имя группы из ответа или явный override |
| POST  | `/api/datasets/import`      | `{groupId:"DEV"}`; только локальный файл         |
| POST  | `/api/datasets/upload`      | Официальная структура с исходным `dataset_group_id`; TXT/PDF используют UPLOAD |
| POST  | `/api/checklists`           | Checklist с ожидаемой текущей версией            |
| POST  | `/api/evaluations`          | `{recordId,checklistId}`; 202 с `evaluating`     |
| POST  | `/api/appeals`              | `{evaluationId,criterionId,comment}`             |
| POST  | `/api/appeals/:id/decision` | `{action,answer,reason}`                         |

`503` + `EVALUATION_DISABLED` означает запрет вызова модели, а не отсутствие сервера. Импорт идемпотентен; изменение содержимого под существующим ID отклоняется. Запись состояния атомарная, мутации последовательные; один процесс владеет файлом. Сервер проверяет входные данные, локальный адрес/Origin и ограничивает JSON-тело 5 МБ. Сеть, публичная авторизация и промышленная база данных требуют отдельной работы перед размещением.

## Расчёт и граница доверия

Основной массив `results` содержит результаты критериев (дополнительные `coaching` и `contact_reason` описаны ниже): `criterion_id`, `status` (`scored`/`not_applicable`), `value`, `reason`, `evidence_ids`, `evidence_kind` (`messages`/`checked_range`). Сервер требует все критерии текущего снимка, проверяет значения шкал, допустимость N/A, непустые причины и существующие ID. Цитаты составляются из исходных реплик на сервере, а не принимаются от модели. Для проверенного диапазона нужны две упорядоченные границы включительно.

Баллы рассчитываются кодом по официальному чек-листу: `100 × сумма(вес × доля шкалы) / сумма применимых весов`. N/A исключается из знаменателя, итог округляется до двух знаков; если применимых критериев с весом нет, итог `null`. Используется десятичное HALF_UP как выбранный способ округления. Грубое нарушение — отдельный безбалльный флаг, оно не обнуляет результат. При апелляции исходные ответы и исходный итог сохраняются, текущие баллы пересчитываются.

Транскрипт в запросе явно отделён от инструкций; аудиоссылки и секреты в prompt не включаются. Неверный JSON или невозможность обоснованной оценки не превращаются в ноль/N/A. Проверка структуры и ссылок не доказывает смысловую правильность вывода модели.

## Проверка без шлюза

```sh
npm run check
npm test
npm --prefix frontend run test:e2e -- --config playwright.backend.config.ts
```

Запускать из корня. `check` проверяет TypeScript сервера и собирает frontend; `test` запускает модульные/HTTP-тесты. Отдельная команда Playwright поднимает синтетические backend/frontend экземпляры на портах 8001/8002 и 5175/5176; нужен установленный Chrome. Тесты используют синтетические транскрипты, временные хранилища и подставной оценщик. Они проверяют HTTP, формулу, сохранение, UI и запрет повторных запросов, но **не подтверждают качество или совместимость реального LLM-шлюза**. Корневой `.env` и настоящий токен для них не нужны и не читаются; обращений к реальному шлюзу нет.

Карта: `src/server.ts` — HTTP/задачи, `store.ts` — хранение, `scoring.ts` — строгая проверка результата и расчёт, `prompt.ts` — контракт модели, `provider.ts` — закрытый одноразовый шлюз, `index.ts` — обычный безопасный запуск.

## Причина обращения и исход

Новый prompt запрашивает `contact_reason` в том же JSON-ответе, что и `results`. Поле сохраняется как необязательное `Evaluation.contactReason`, поэтому старые сохранённые оценки продолжают открываться. Формат: `taxonomyVersion: 1`, `primary`, `secondary` (до 3 уникальных категорий без основной), `summary`, `reason`, `evidenceIds`, `resolution: {status, reason, evidenceIds}`. Справочник: `frontend/src/lib/contactReasons.ts`. Исходы: `resolved`, `unresolved`, `unknown`.

Для определённой причины и подтверждённого исхода нужны доказательства из того же разговора. Сервер отклоняет неизвестные категории, неверные версии, дубли и чужие ID. Классификация не меняет баллы и сохраняется при пересмотре оценки. Старый ответ только с `results` совместим: отсутствие классификации показывается явно, а не подменяется категорией `unknown`.

Реальная смысловая точность новой классификации ещё не проверялась. Синтетические тесты проверяют контракт и сохранение, а не качество модели. Отчёт не вызывает модель; классификация появится после следующего отдельно разрешённого анализа. Старые записи автоматически не переоцениваются.

## Обучающие рекомендации оператору

В результат критерия добавлено optional `coaching: {response, explanation, needsContext, messageIds}`. Новый prompt запрашивает его при нарушении; `null`/отсутствие сохраняет совместимость со старыми ответами. `needsContext=true` требует `response=null`; иначе нужна непустая предложенная реплика. Строки ограничены 2000 символами, доказательства — 1–100 уникальных ID этого разговора. Рекомендация для исходно выполненного или N/A критерия отклоняется. При апелляции рекомендация сохраняется, но интерфейс скрывает её, если текущий ответ больше не является нарушением.

Рекомендации и причины обращения запрашиваются вместе с основной оценкой, без второго вызова модели. В prompt запрошены короткие формулировки без выдуманных бизнес-условий. Это увеличивает объём ответа: экономия относительно отдельной модели не измерялась. Графики, фильтры, поиск и статистика выполняются кодом. Отдельную генеративную модель для советов не добавляли; локальная Laya классифицирует причины обращений, как описано ниже. Тарифы и качество советов потребуют отдельного сравнения.

## Локальная Laya

Полная инструкция: [laya/README.md](laya/README.md). `--local-laya` подключает offline worker после scoring Kimi; общий `npm run dev` добавляет этот флаг при наличии локального окружения и весов. Ошибка Laya не отменяет оценку Kimi. POST `/api/evaluations/:id/classify-reason` предназначен для старых оценок и не расходует шлюзовую квоту. Сервисы классификации, провайдеры и их ошибки разделены; секретный `.env` для Laya не используется.

## Изменение критериев перед следующим анализом

В «Чек-листах» можно добавить или удалить критерий, изменить правило, тип ответа и вес, затем нажать «Сохранить чек-лист». Сервер сохраняет новую версию полного списка. В карточке разговора выберите нужный чек-лист: блок «Правила следующей оценки» показывает актуальную версию и веса, даже если ниже открыт старый результат. Нажатие «Оценить заново» использует сохранённый список на момент запуска.

Новые критерии передаются модели через динамический prompt; удалённые не передаются. Сервер отклоняет ответ с пропущенными или лишними критериями. Вес применяется кодом, а итог нормируется до 100: например, если применимые веса суммарно 125, выполненный критерий с весом 25 даёт 20 итоговых баллов. N/A исключается из знаменателя. Грубый флаг остаётся безбалльным.

Прошлые результаты, их снимки правил и апелляции не переписываются. Изменение правил во время уже начатого анализа не меняет его снимок. Отдельный «Пример правильного подхода» использует сохранённый снимок правил и результата, в том числе для пользовательского чек-листа. Запускается только своей кнопкой и не изменяет баллы. Удаление «Выявления потребности» не отменяет оценку, но Laya не сможет классифицировать причину без соответствующего фрагмента.

## Импорт по ссылке

`src/dataset-import.ts` получает официальный JSON по публичной HTTPS-ссылке, до 5 МБ/20 секунд. DNS проверяется до подключения, выбранный публичный IP закрепляется в HTTPS lookup; сертификат проверяется по исходному hostname. Redirects, HTTP, private/reserved IP, credential URL и произвольные порты запрещены. URL/подпись не сохраняются, ошибки фиксированные без ответа внешнего сервера. `groupId` при наличии заменяет `group_id`, проверяется совпадение с JSON. По умолчанию группа определяется по `data.dataset_group_id`. LLM не вызывается; импорт использует существующий атомарный merge и сохраняет историю.

PDF извлекается на frontend локально через bundled PDF.js worker; сервер получает уже разобранный транскрипт через `/api/datasets/upload`. Официальные JSON-файлы и API-наборы сохраняют исходные ID и аудиоссылки. TXT/PDF используют генерируемые ID группы UPLOAD. Сервер не скачивает записи автоматически.
