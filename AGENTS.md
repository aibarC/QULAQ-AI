# Работа AI-агентов над QULAQ-AI

## Текущий проект и совместная работа

- Этот репозиторий — QULAQ-AI, CQA для хакатона. Локальная исходная папка называлась QULAQ2; это не другой продукт.
- Сначала прочитай README.md, WORKFLOW.md, DEVELOPMENT_PLAN.md и CONTRIBUTING.md. Для frontend также TEAMMATE_UI_BRIEF.md. OPTIONAL_FEATURES.md не входит в обязательный объём.
- Правила ниже первоначально перенесены из Qulaq. Упоминания PRODUCT.md, DECISIONS.md, HANDOFF.md, live STT и сценариев встреч относятся к старому проекту и не требуют их создания или переноса. Текущая задача — оценка готовых транскриптов, без STT.
- aibarC отвечает за backend, LLM, расчёт, хранение и интеграцию; bagdaulet-dev — за frontend и клиентский адаптер. Не редактируй чужую зону параллельно без согласования. Общую конфигурацию и серверный формат координирует aibarC.
- После первоначальной загрузки не пушь напрямую в main: работай в отдельной ветке codex/backend-<task> или codex/frontend-<task>, открывай PR в main. Один владелец на рабочую ветку; не используй одну ветку для двух параллельных агентов.
- Перед началом и push проверь git status, текущую ветку, origin и свежий origin/main. Ожидаемый origin — https://github.com/aibarC/QULAQ-AI.git либо SSH-эквивалент.
- На чистой main обновляйся через git pull --ff-only. Для опубликованной рабочей ветки при необходимости вливай origin/main обычным merge; не переписывай опубликованную историю. При конфликте прочитай обе версии, сохрани нужные изменения и проверь результат; не выбирай всю чужую или свою сторону вслепую.
- Не применяй force push, reset --hard, git clean или удаление чужих веток ради устранения расхождения. Не прячь и не уничтожай незакоммиченные изменения автоматически.
- Пушь только свою рабочую ветку; при отклонённом push сначала fetch и разбор расхождения. Подробный процесс, команды и порядок merge — CONTRIBUTING.md.
- Эти правила являются соглашением команды. Наличие технической защиты main проверяется отдельно; не заявляй её включённой только на основании файла.

## Контекст и приоритеты

- Сначала прочитай README.md, PRODUCT.md и DECISIONS.md.
- Актуальные указания пользователя имеют приоритет над этими файлами. Архив хранит историю и может содержать устаревшие или отвергнутые предложения.
- Сохраняй различие между подтверждённым решением, предложением агента, гипотезой и реализованной функцией.
- Сейчас сформировано видение. Изменение кода и запуск интеграций должны соответствовать конкретному запросу пользователя. Не превращай запрос описать продукт в начало разработки.
- Общайся по-русски, конкретно. На примере показывай, что человек видит, выбирает и получает. Не подменяй ответ очередным общим описанием.
- Если пользователь просит исправить сценарий, исправляй его целиком с учётом замечаний. Сначала проверь контекст, чтобы не повторять уже решённые вопросы.
- Рутинные обратимые действия в пределах запроса выполняй самостоятельно. Не запрашивай повторное согласие на уже разрешённое. Соблюдай фактические разрешения среды.

## Делегирование

- Делегируй только самостоятельные части, когда параллельная работа заметно ускоряет результат или нужна независимая проверка. Простые задачи выполняй сам; учитывай суммарный расход токенов всех агентов.
- Переиспользуй существующие сессии субагентов. Главный агент координирует, интегрирует и проверяет результат.
- Для существенного сценария используй независимую проверку удобства и критику полноты. Рецензия по тексту не равна испытанию с пользователями.
- Не создавай пользовательские чаты автоматически.
- Передавай агентам ограниченную задачу, необходимые факты и требования к результату. Разделяй владение файлами, если агенты редактируют параллельно.

## Продукт и доказательства

- Проверяй решения на нескольких личных сценариях, включая питч и разговор с преподавателем. Не меняй смысл вкладок и функций без объяснения.
- Различай изложение мысли, ответ и согласие. Сохраняй ручные поправки пользователя.
- Для памяти учитывай отдельно читателей, связь с человеком/группой и допустимую аудиторию встречи. Связь с группой не означает рассылку или публичный доступ.
- Не заявляй качество смешанной речи, распознавания спикеров, задержки, безопасности или наличие клиентов без соответствующих проверок.
- Маркетинговые заявления конкурентов атрибутируй. Для выводов об активности или продажах ищи независимые источники.
- Числа, цены, сроки, технологии и интерфейсные детали из архивов не считай утверждёнными.
- После разрешённой реализации проверяй нормальный пользовательский путь и существенные ошибки. Отделяй сценарное демо от реальной обработки.

## Общая библиотека скиллов

- Репозиторий https://github.com/aibarC/agent-toolkit, локальная копия /Users/srkaibar/agent-toolkit.
- При первом обращении к библиотеке в новой сессии перед показом каталога, подбором, установкой или изменением скиллов проверь origin. Он должен вести именно на github.com/aibarC/agent-toolkit по HTTPS или SSH. При несовпадении останови обновление.
- Проверь рабочее дерево и успешно выполни git fetch origin refs/heads/main:refs/remotes/origin/main. Сравни HEAD со свежим ref.
- Автоматически обновляй только чистую main командой git merge --ff-only refs/remotes/origin/main. После fast-forward проверь чистоту дерева и равенство HEAD и origin/main. Только тогда называй копию актуальной на момент fetch.
- При грязном дереве, другой ветке, локальных коммитах или расхождении ничего не перезаписывай и сообщи состояние. Ошибка fetch или отсутствие сети означает, что актуальность не проверена.
- Затем прочитай README.md и CATALOG.md библиотеки. Зафиксируй используемый SHA на время задачи. Перед публикацией повтори проверку GitHub. Полная синхронизация на каждой правке с уже выбранным скиллом не нужна.
- Проверяй фактические глобальные и проектные папки, цели ссылок и доступность текущему агенту. Каталог не является реестром установок.
- Сначала ищи в общей библиотеке. Новое добавляй с источником и лицензией в запрошенную область установки.

## Эффективность и расход токенов

Предпочтение пользователя: выполнять задачу до результата, экономить токены за счёт точного поиска и отсутствия повторов, сохраняя необходимые проверки.

- Перед выводом проверяй прямые данные. Размер репозитория в поиске не доказывает его пустоту: проверь содержимое и ветки. Различай локальную папку, GitHub-репозиторий и конкретную ветку.
- Сначала используй уже полученный контекст и результаты. Повторяй чтение и проверки при изменении состояния, устаревании данных или конкретном сомнении.
- Ищи адресно: известная папка → список файлов/rg → нужный фрагмент. Не начинай с рекурсивного обхода всего профиля пользователя. Ограничивай объём вывода инструментов.
- В каталоге инструментов выбирай нужные имена и описания. Полную схему читай только для выбранного инструмента; не выводи схемы всех похожих инструментов.
- Объединяй независимые чтения и проверки в один вызов, когда это удобно. Зависимые действия выполняй последовательно и проверяй ошибки.
- Подключай только относящиеся к задаче скиллы. Не запускай исследование, установку зависимостей или разработку сверх запрошенного объёма.
- Субагенту передавай узкую задачу и минимально достаточный контекст. Не дублируй его работу; запрашивай краткий результат с доказательствами и ограничениями.
- Не опрашивай неизменное состояние частыми вызовами. Используй ожидание завершения и разумные интервалы.
- Пиши коротко: результат, существенные факты, ограничение или следующий необходимый шаг. Не пересказывай каждый вызов инструмента и уже сказанное.
- Не задавай повторные вопросы о разрешённых действиях и доступных данных. Спрашивай, когда ответ действительно влияет на результат и его нельзя получить из контекста.
- Проверяй изменения соразмерно риску. После успешных достаточных проверок завершай задачу; расширяй проверки при новых ошибках или изменениях.
- Ошибку признавай прямо и исправляй выполненным действием. Обновляй ошибочные отчёты, чтобы следующие агенты не повторяли неверный вывод.
