# План разработки CQA для двух участников

План будущей работы, а не отчёт о реализации. Обязательный процесс описан в [WORKFLOW.md](WORKFLOW.md); отдельная спецификация интерфейса для напарника — [TEAMMATE_UI_BRIEF.md](TEAMMATE_UI_BRIEF.md). Стек, доступ к Kazakhtelecom API и конкретные модели пока не подтверждены. Работа идёт параллельно по готовым результатам, без искусственных часовых блоков согласования.

## Ответственность и владение

| A — пользователь + главный AI | B — напарник + его AI |
|---|---|
| Backend, импорт наборов, API приложения и хранение | Frontend: визуальный стиль, компоненты, навигация и состояния |
| LLM, prompt всех восьми критериев, проверка результата и доказательств | Список реальных диалогов, карточка, транскрипт, доступ к аудио |
| Расчёт баллов и N/A, версии чек-листов и оценок | Редактор чек-листа, показ результатов и переход к доказательствам |
| Апелляции, решения, overrides и пересчёт | Подача и рассмотрение апелляций, история и отображение итогов |
| Качество RU/KZ/EN, задержка, стоимость, общая интеграция | Проверка удобства, визуальная подготовка демо |

Предлагаемые зоны файлов после выбора стека: A — `server/`, `storage/`, `llm/`, `evaluation/`, серверные контракты и тесты логики; B — `frontend/`, стили, компоненты и клиентский адаптер API. A владеет общей конфигурацией запуска. Названия каталогов не означают, что они уже существуют.

B не реализует отдельную серверную систему, хранение или вторую формулу баллов в браузере. По явной договорённости он может быстро сделать dev-server/proxy для datasets в отдельном файле: до передачи им владеет B, после приёмки — A. Секретная подписанная ссылка и ключи остаются на сервере.

## Параллельный старт

Коротко выбрать/подготовить общий репозиторий, согласовать стек и границу frontend/backend — ориентир 5–10 минут, не обязательная встреча и не условие начала UI-работы. Документы пока находятся в QULAQ2; общий рабочий репозиторий не считается уже настроенным. Не пытаться заранее спроектировать весь API.

- **B начинает сразу:** интерфейс списка и карточки на известном формате настоящих conversations. Пока серверный endpoint готовится, можно использовать локальный пример его реального ответа без секретной ссылки. Тестовые оценки показываются только как явно обозначенные примеры.
- **A начинает сразу:** минимальный серверный импорт DEV и стабильные ID, затем первый рабочий вызов доступной LLM для оценки всех восьми критериев. Отдельный summary не является первым этапом.
- Как только появляется первый настоящий результат, A передаёт его B. Не ждать сравнения всех моделей или завершения benchmark. B подключает результат через один frontend-адаптер, чтобы изменения формата не требовали переписывать компоненты.
- Остальные интерфейсы передаются небольшими порциями: чек-лист → запуск и чтение оценки → апелляция → решение. Для каждой передачи достаточно примера запроса, ответа, ошибки и краткого согласования. Уже используемые поля не менять молча.

## Короткий протокол данных для B

**Разговоры.** Источник организаторов возвращает `conversation_id`, `channel`, `language`, `transcript`, `audio_url`. Реплика содержит `timestamp`, `speaker`, `text`; роли — `client`, `operator`, `bot`, `system`. Имени сотрудника нет: не придумывать его. Метки времени сохраняются как есть; для звонков не обещать точный seek по ISO-времени до проверки соответствия записи.

На входе A назначает стабильный внутренний `record_id`, связанный с набором и `conversation_id`, и `message_id` каждой реплике. Повторный импорт той же записи не должен создавать новые ID. B получает эти ID и использует их для списка и навигации; не генерирует их из отсортированного или отфильтрованного списка.

**Оценка.** A назначает стабильные `criterion_id`; каждый запуск получает отдельный `evaluation_id`. Первый пример ответа должен содержать `evaluation_id`, `record_id`, снимок/версию чек-листа, результаты критериев, рассчитанный итог и флаг грубых ошибок. По критерию нужны `criterion_id`, ответ/значение или N/A, объяснение, вес, баллы и evidence с ID сообщения либо проверенного диапазона. Точные имена полей уточняются первым рабочим ответом; A владеет серверным форматом, B — преобразованием в модель отображения.

**Границы.** A проверяет допустимые шкалы, N/A и существование evidence, рассчитывает итог кодом и сохраняет результат. B отображает ответ сервера; не превращает отсутствующий результат или ошибку в нулевой балл. До готовности endpoint допускается тестовый пример соответствующей формы, но не имитация успешного сохранения в реальном режиме.

**Апелляции.** Обращение связано с `evaluation_id` и `criterion_id`, содержит комментарий. Решение — подтверждение либо допустимое новое значение и обязательная причина. Backend хранит исходную оценку отдельно от человеческих overrides и возвращает пересчитанный итог. Комментарий сам по себе не запускает LLM и не меняет балл.

## Этапы по готовым результатам

| Результат | A | B | Критерий готовности |
|---|---|---|---|
| Реальные разговоры доступны | Импорт по `group_id`, стабильные ID, минимальный API | Список, карточка, роли, время, аудио, загрузка и ошибка | DEV открывается в приложении; выбранная строка показывает правильный разговор |
| Первая настоящая оценка | Baseline всех восьми критериев, валидация, расчёт, сохранение; немедленная передача ответа | Кнопка оценки, ожидание/ошибка, критерии, N/A, итог, доказательства | Оценка выбранного диалога проходит от кнопки до сохранённого результата |
| Изменяемые правила | Сохранение и версии чек-листа; новый критерий реально попадает в запрос модели | Редактор формулировок, весов, типов, шкал и N/A | Критерий добавляется или заменяется через UI и применяется без правки кода |
| Полный цикл апелляции | Создание, чтение, решение с причиной, overrides, пересчёт | Мои апелляции, очередь проверяющего, форма решения, история | Видны исходная оценка, решение и текущий итог; подтверждение и изменение работают |
| Устойчивый MVP | Проверки арифметики, ошибок, сохранности, версий, качества | Проверка всех состояний, навигации, читаемости и обновления страницы | Обязательный путь работает после перезагрузки; сбой не выглядит как успех |
| Готовность к сдаче | README, конфигурация, стоимость и ограничения модели, обработка контроля | Проверка запуска на втором устройстве, демонстрационный путь и визуальная доводка | Открытый репозиторий подготовлен, ссылка передана организаторам; защита укладывается в 5 минут |

Интеграция начинается с первого endpoint и продолжается на каждом этапе. B не ждёт «финального контракта» для UI-работы; изменения модели локализуются в адаптере результата.

## Модель и проверка качества

1. Проверить фактический доступ и выполнить baseline доступной моделью. Kazakhtelecom остаётся кандидатом до успешного запроса и проверки доступных моделей/ограничений. Если доступ блокирует работу, ограничить диагностику и перейти к доступному варианту.
2. Провести быстрый технический отсев на **одном RU, одном KZ и одном EN** диалоге: есть ли все критерии, корректный формат, допустимые значения и реальные evidence. Эти три примера не доказывают точность и не используются для заявления качества языка.
3. Только после рабочего baseline сравнивать максимум 2–3 доступные модели одинаковым протоколом. До настройки выделить небольшую ручную выборку и оставить часть примеров нетронутыми. Практический ориентир — 18 диалогов: 9 настройки и 9 проверки, по 3 на язык в каждой части. Если времени мало, уменьшить объём и явно указать его. Не размечать и не «обучать на всех 65» ради самого процесса.
4. A ведёт разметку и анализ; B кратко независимо проверяет спорные ответы и часть примеров, не останавливая основной UI-поток. Записывать неоднозначности: ручная оценка не безусловная истина.
5. Проверять совпадение по каждому критерию, N/A, величину ошибки шкальных оценок, пропуски/ложные флаги грубых ошибок, валидность JSON/схемы, существование и смысловую пригодность evidence. Измерять полную задержку и стоимость всех вызовов, включая повторы. Неизвестный тариф не считать нулевым.
6. Нетронутые примеры открыть после фиксации модели и prompt. После исправлений по их результатам это уже набор разработки, а не независимая проверка. Контроль организаторов не использовать для подгонки ожидаемых ответов.

Ограничения озвучить честно: маленькая выборка, субъективные критерии, отсутствие выданной базы правильных бизнес-консультаций. Готовый текст не подтверждает анализ интонации. Не откладывать передачу рабочего результата B ради поиска «лучшей» модели.

## Обязательные проверки и работа без ожидания

**A:** корректный расчёт (например, 7/10 при весе 15 = 10,5 до перераспределения), N/A и округление; грубая ошибка отдельно; невалидные ответы и таймауты; защита исходной оценки и правил при пересмотре; сохранность после перезапуска; отсутствие дублей открытой апелляции; доступность импорта контрольного `group_id`. Транскрипт рассматривается как данные, а не инструкции модели.

**B, пока ждёт endpoint:** закончить обязательные экраны и формы; переходы к репликам; длинные RU/KZ/EN тексты; состояния пустого списка, ожидания, ошибки и недоступного аудио; клавиатурную навигацию; визуальную и адаптивную доводку; проверку реальных данных и подключение уже готовых endpoints. Комментарии и транскрипты выводятся как текст, не исполняемый HTML.

**Вместе:** импорт → оценка → доказательство → апелляция → подтверждение/изменение с причиной → итог → обновление страницы. Добавить критерий без кода; убедиться, что новая оценка не затирает решение человека. Проверить запуск по README и отсутствие секретов/частных записей в публичном Git.

После готовности обязательного пути B может добавить работающие поиск, фильтры, сворачивание успешных критериев, сравнение сохранённых исходного и итогового результатов или экспорт доступных данных. Не делать декоративные кнопки, вымышленные показатели и функции, которые только выглядят работающими. Массовая оценка полезна после MVP; если без неё контрольный набор не удаётся обработать вовремя, A делает минимальную очередь запуска приоритетной задачей сдачи.

## Контроль и защита

- **T+23 часа:** организаторы открывают контрольные транскрипты и сообщают `group_id`. Импортировать через тот же путь, заранее запустить реальные оценки, проверить сохранение и ошибки.
- **T+24 часа:** стоп-код, зафиксировать последний коммит. После этого разрешены обработка данных и изменение чек-листа через UI зафиксированной версии, но не изменение кода.
- До стоп-кода: открытый Git-репозиторий, заранее переданная ссылка, понятный README. Защита максимум 5 минут: интерфейс/диалог; оценка, evidence, переход, N/A и итог; апелляция и пересчёт; изменение критерия и применение. Для платной модели назвать модель и приблизительную стоимость всей оценки.

**Auto Improve AI — вне MVP.** Согласованный вариант описан в [OPTIONAL_FEATURES.md](OPTIONAL_FEATURES.md): ИИ предлагает уточнение инструкций из подтверждённой ошибки, проверяющий отдельно утверждает его. Это не обучение весов модели. Функция зависит от серверной логики, prompt и проверки качества, поэтому не является независимой простой задачей B. Сейчас апелляция меняет сохранённую оценку и итог. STT, персональные кабинеты и обучение собственной модели также не входят в этот план.
