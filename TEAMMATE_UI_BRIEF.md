# QULAQ2 — задание напарнику на интерфейс

Это спецификация для разработки, а не отчёт о готовом приложении. Основа процесса зафиксирована в WORKFLOW.md. Названия и расположение элементов ниже — выбранный интерфейс для реализации требований хакатона.

## 1. Ответственность и границы

**A — основной разработчик:** сервер, подключение и выбор модели, импорт через API организаторов, валидация ответа модели, расчёт баллов, постоянное хранение, логика апелляций и решений, API приложения.

**B — напарник:** frontend, экраны, формы, навигация, транскрипт и аудио, фильтры, отображение состояний и ошибок, клиентский адаптер к API A. Пока сервер не готов, B использует демонстрационный адаптер и локальную загрузку данных для разработки.

B не реализует второй независимый сервер, собственную формулу итоговых баллов, постоянное хранение производственных результатов или отдельную бизнес-логику апелляций. UI отправляет команды серверу и отображает возвращённое состояние. Предпросмотр нового итога при ручном изменении допустим, если A предоставляет соответствующий endpoint; до этого предпросмотр не показывать, арифметику во frontend не дублировать.

Можно начинать UI без готовой модели. Компоненты должны работать с внутренним представлением результатов через сменный клиентский адаптер, а не напрямую с ответом конкретного LLM-провайдера.

## 2. Данные и безопасный путь загрузки

DEV API ранее проверен: 65 разговоров, 60 чатов и 5 звонков; 35 RU, 15 KZ, 15 EN. Это не означает, что локальная копия набора уже сохранена: наличие dev-файла нужно проверить или получить его у A.

Поля записи:

- `conversation_id` — ID разговора;
- `channel` — `agent chat` или `voice call`;
- `language` — RU, KZ или EN;
- `transcript` — массив объектов `timestamp`, `speaker`, `text`;
- `audio_url` — ссылка для звонка, `null` у чата.

Роли сообщений: `operator`, `client`, `bot`, `system`. Отдельного поля имени сотрудника нет. Не придумывать имена, владельцев записей и персональные рейтинги.

Рабочий импорт выполняется через сервер A с параметром `group_id`. Подписанную ссылку API организаторов нельзя вшивать во frontend, включать в клиентскую сборку или публиковать в Git.

Пока endpoint A не готов, разрешён локальный JSON-файл набора, исключённый из Git и читаемый локальным dev-сервером только для разработки. Такой файл нельзя включать в публичную сборку. Данные для разработки и их наличие согласовать с A; не считать их заранее сохранёнными.

Все записи массива отображаются автоматически. Не создавать вручную 65 отдельных компонентов или жёстко зашитых карточек. Должны работать и другой размер набора, и новый `group_id` контрольных данных.

Импорт и оценка — разные действия. Импорт сам по себе не присваивает баллы. Загрузка отдельных аудиофайлов и транскрибация в эту версию не входят.

## 3. Визуальная оболочка

- Название: QULAQ2; пояснение «Контроль качества диалогов».
- Светлый интерфейс: нейтральный фон, белые рабочие панели, один зелёный акцент. Чёткие заголовки и состояния, достаточно воздуха, без декоративных графиков.
- Слева навигация, сверху заголовок текущего раздела и переключатель **«Пользователь / Проверяющий»**.
- Переключатель — демонстрация ролей без регистрации, не система авторизации.
- Пользователь видит **«Диалоги», «Чек-листы», «Мои апелляции»**.
- Проверяющий видит только **«Апелляции»**. Полный разговор доступен внутри обращения.
- Не добавлять Dashboard, список сотрудников, рейтинги людей и пустые аналитические виджеты.
- Кнопки, поля и ссылки доступны с клавиатуры; фокус видим. Статусы различаются текстом, а не только цветом.

## 4. Пользователь: «Диалоги»

### До первого импорта

- Заголовок «Диалоги».
- Поле **«Набор»**, начальное значение `DEV`.
- Кнопка **«Загрузить набор»**.
- Пояснение: «Получим готовые транскрипты и ссылки на записи».
- Пустое состояние: «Набор ещё не загружен».
- Нет кнопок «Записать аудио» и «Загрузить аудиофайл».

### Импорт

Frontend передаёт `group_id` серверу A. Пока запрос выполняется — индикатор загрузки и защита от повторной отправки. После успеха отображается весь полученный набор и реальное количество записей.

Повторный импорт не должен создавать дубли или стирать оценки: это гарантирует сервер A; UI отображает его результат. При ошибке показать понятное сообщение и «Повторить», уже доступные данные не скрывать.

В локальном режиме разработки явно показывать «Локальный набор для разработки». Не изображать чтение файла как успешное обращение к организаторскому API.

### Список

Колонки:

1. ID разговора;
2. канал;
3. язык;
4. статус оценки;
5. итог;
6. число открытых апелляций, если есть.

Строка открывает карточку разговора. Сверху — поиск по ID, фильтры по каналу, языку и статусу. Итог до оценки — «—», не ноль.

Состояния оценки: **Не оценён / Оценивается / Оценён / Ошибка**. Факт ручного пересмотра и число апелляций отображаются отдельно. Данные статусов приходят из адаптера, затем из сервера.

## 5. Карточка диалога

### Верхняя полоса

- **«← К диалогам»**, ID, канал, язык.
- Выбор сохранённого чек-листа.
- Кнопка **«Оценить»**; после первого результата — **«Оценить заново»**.
- Если сервер возвращает несколько результатов, компактный выбор запуска с датой и версией чек-листа.

### Две рабочие колонки

**Слева, примерно 50–55% ширины:** полный транскрипт с ролями и временем. Для звонка над ним аудиоплеер или ссылка на запись.

**Справа, примерно 45–50%:** выбранный чек-лист, оценка, критерии, доказательства и действия.

На узком экране колонки складываются вертикально. На ноутбуке остаются рядом. Области прокрутки должны позволять открыть доказательство, не потеряв выбранный критерий.

Реплики оператора и клиента визуально различаются. Бот и системные сообщения компактнее, но доступны и не теряются: они могут быть доказательствами.

Сохранять исходные временные метки. Для ISO-времени допустимо компактное отображение с полным оригиналом в подсказке. Не вычислять и не обещать точное смещение аудио, пока A не предоставит проверенное сопоставление времени.

### До оценки

Справа показать выбранный чек-лист, количество критериев и кнопку оценки. Не отображать фиктивные баллы.

### Во время оценки

Показать «Оценка выполняется». Не выдумывать процент прогресса. Если сервер отдаёт реальные этапы — отображать их. Транскрипт остаётся доступным.

При ошибке показать отдельное состояние с повторным запуском. Не превращать ошибку вызова или неверный формат ответа в нулевую оценку либо N/A.

### Результат

- Общий итог **XX,XX / 100**, полученный от сервера.
- Отдельный заметный флаг грубого нарушения.
- Результаты секций, если они предоставлены.
- По каждому критерию: название, ответ/оценка по шкале, вклад в итог, вес, объяснение, доказательства, кнопка **«Оспорить»**.
- Ошибки и потерянные баллы можно располагать первыми; успешные критерии также доступны.
- N/A показывать с причиной неприменимости, не как штраф.
- Клик по доказательству прокручивает транскрипт к сообщению или диапазону и временно выделяет его.
- Для отсутствующего действия показывается проверенный участок, а не выдуманная цитата.
- Нет обязательного подтверждения каждого критерия.

После ручного пересмотра показать исходный и новый ответы, например «ИИ: 10 → Проверяющий: 15», причину и ссылку на решение. Исходная оценка остаётся доступной.

Повторная оценка создаёт отдельный результат на стороне A. UI не перезаписывает историю и не переносит решения между разными запусками автоматически.

## 6. Подача апелляции

Кнопка «Оспорить» открывает панель или модальное окно:

- ID диалога;
- название и формулировка критерия;
- исходная оценка;
- обязательное поле **«Почему вы не согласны?»**;
- **«Отправить апелляцию»**, **«Отмена»**.

Frontend отправляет обращение серверу A. Только после успешного сохранения:

- показать «Апелляция отправлена проверяющему»;
- дать ссылку **«Открыть апелляцию»**;
- отобразить на критерии «Ожидает рассмотрения»;
- обновить список «Мои апелляции» и счётчик открытых обращений.

Комментарий сам по себе не меняет баллы и не отправляется модели. При ошибке сохранения текст пользователя сохраняется в форме, а статус успеха не показывается.

Если сервер сообщает о существующем открытом обращении на тот же критерий того же результата, открыть его вместо создания дубля.

## 7. Пользователь: «Мои апелляции»

Таблица: ID обращения, ID разговора, критерий, дата, статус, решение. Фильтры **«Ожидают / Рассмотрены / Все»**.

В карточке ожидающего обращения доступны исходная оценка и отправленный комментарий. В рассмотренном — исходная оценка, решение оставить/изменить, новый ответ и причина проверяющего.

Кнопка **«Открыть разговор»** ведёт к соответствующему результату. Пользователь не редактирует решение проверяющего.

В демо это обращения одного условного пользователя. Не изображать настоящее разграничение доступа по аккаунтам.

## 8. Проверяющий: «Апелляции»

### Очередь

- Ожидающие обращения первыми.
- Колонки: ID обращения, ID разговора, критерий, дата, статус.
- Счётчик открытых обращений.
- Строка/кнопка **«Рассмотреть»**.
- Рассмотренные обращения доступны через фильтр истории, не исчезают.

### Карточка обращения

Верх: ID, статус, **«← К апелляциям»**.

Слева: полный транскрипт и аудио, переходы к доказательствам.

Справа по порядку:

1. исходное правило и допустимая шкала того запуска;
2. ответ и объяснение ИИ;
3. комментарий пользователя;
4. форма решения.

Форма решения:

- **«Подтвердить исходную оценку»** или **«Изменить оценку»**;
- при изменении — выбор допустимого ответа/значения, полученного из снимка критерия;
- N/A доступен только если разрешён критерием;
- обязательная **«Причина решения»**;
- **«Сохранить решение»**.

Frontend отправляет решение A. Сервер проверяет допустимость, сохраняет решение и пересчитывает итог. UI показывает новые значения только после подтверждённого ответа.

Предпросмотр изменения итога добавлять только при наличии серверной функции A. Без неё не показывать локальный расчёт.

При успехе видны сохранённое решение, причина, новый итог и возврат в очередь. При ошибке форма не теряет введённые данные, обращение не считается рассмотренным.

У проверяющего нет самостоятельного раздела всех диалогов или редактора чек-листов; необходимый разговор открывается внутри апелляции.

## 9. Пользователь: «Чек-листы»

Начальная конфигурация — восемь критериев из PDF. Экран показывает сохранённые конфигурации и редактор выбранной.

Поля конфигурации:

- название;
- секции, если используются;
- список критериев.

Поля критерия:

- название и формулировка;
- тип ответа;
- вес;
- разрешение N/A и условие неприменимости;
- для числового типа — допустимые ступени и описание каждой;
- для грубого нарушения — признак отдельного безбалльного критерия.

Кнопки: **«Добавить критерий»**, **«Сохранить чек-лист»**. Показать индикатор несохранённых изменений и ошибки полей. Проверка формы не заменяет валидацию сервера.

Сохранение отправляет конфигурацию A. Оно не запускает оценку и не переписывает предыдущие результаты. Результат должен показывать ту версию правил, по которой был получен.

## 10. Адаптер и разработка без модели

Компоненты читают внутреннее представление данных через клиентский адаптер. Конкретные HTTP-маршруты и wire-формат согласуются с A; не зашивать в компоненты формат сырого ответа LLM.

Минимальные операции адаптера:

- получить/импортировать набор и список диалогов;
- получить карточку диалога и результаты;
- получить/сохранить чек-листы;
- запустить оценку и получить её состояние;
- создать/получить апелляцию;
- получить очередь и историю;
- отправить решение проверяющего.

Нужны стабильные идентификаторы разговора, сообщения, чек-листа/версии, результата, критерия и обращения.

Сначала может работать in-memory mock-адаптер, имитирующий переходы для разработки UI. Он не доказывает постоянное хранение и не заменяет сервер A. Локальные настройки интерфейса можно хранить отдельно, но нельзя выдавать это за сохранение реальных результатов и обращений.

На демонстрационной оценке постоянно показывать **«Демонстрационная оценка — ИИ не запускался»**. Не присваивать реальные нарушения реальным разговорам выдуманными mock-ответами. Для полного демонстрационного пути использовать отдельный явно учебный пример или согласованный fixture. Реальный импорт не должен автоматически создавать mock-баллы всему набору.

Все серверные состояния — загрузка, пусто, успех, ошибка — должны иметь явное отображение. Если данные после reload ещё не загружены, не подменять их пустой историей до ответа сервера.

## 11. Порядок реализации

Это порядок приоритета экранов, а не запрет на раннюю интеграцию. Как только A передаёт готовый endpoint или настоящий результат, B сразу подключает соответствующую операцию. Не ждать завершения всех mock-экранов перед первой реальной оценкой.

1. Оболочка ролей, навигация, адаптер и локальная загрузка набора для разработки.
2. Список всех записей, фильтры, карточка, транскрипт и аудио.
3. Редактор чек-листа и подключаемое отображение результатов с доказательствами.
4. Формы подачи и рассмотрения апелляций, пользовательская история, все переходы на mock-адаптере.
5. Подключение API A, проверка обновления состояния и сохранения после reload.
6. Ошибки, пустые состояния, повторная оценка без потери истории, визуальная полировка.

## 12. Полезные дополнительные UI-функции

После основного пути B может независимо добавить:

- поиск по тексту транскрипта;
- фильтры ошибок, успешных и N/A критериев в карточке;
- сворачивание успешных критериев при сохранении доступа к объяснениям;
- удобное сравнение исходной и финальной оценки;
- сохранение позиции списка/фильтров при возврате из карточки.

Массовая оценка зависит от серверной очереди A и не входит в независимые задачи B. Добавлять её только после согласования backend-поддержки.

Пока не нужны: обучение модели, Auto Improve, транскрибация, отдельные аккаунты, сотрудники и их рейтинги, внешние уведомления, декоративные аналитические панели.

## 13. Критерии готовности интерфейса

- Все записи набора отображаются из данных, без ручных карточек.
- Из списка открывается правильный разговор, включая звонок с аудио.
- Критерий ведёт к правильному сообщению/участку.
- N/A, ошибка оценки и нулевой балл визуально различимы.
- Пользователь подаёт обращение и видит его статус.
- Проверяющий находит то же обращение, видит весь контекст и сохраняет решение через API A.
- Пользователь видит решение и актуальный итог в исходной карточке.
- Исходная оценка и рассмотренные обращения не исчезают.
- На mock-ответах видна маркировка демонстрации; секретной API-ссылки нет в клиентском коде.
- UI не дублирует серверную арифметику, постоянное хранение и бизнес-логику A.
