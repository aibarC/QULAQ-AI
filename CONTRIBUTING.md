# Совместная работа над QULAQ-AI

Общий репозиторий: https://github.com/aibarC/QULAQ-AI

## Ответственность

- **aibarC:** сервер, модель, prompt, валидация, расчёт, хранение, логика апелляций, общая конфигурация и интеграция.
- **bagdaulet-dev:** интерфейс, стили, компоненты, формы, навигация, клиентский адаптер. Начать с TEAMMATE_UI_BRIEF.md.
- Структура каталогов будет выбрана при реализации. Предлагаемые зоны: backend — server/, storage/, llm/, evaluation/; frontend — frontend/.
- Общие manifest/lock-файлы, конфигурацию запуска и формат API меняет один назначенный участник за раз. Согласовать изменение до параллельного редактирования.
- Не ждать завершения целых модулей: небольшие PR и первые реальные примеры передавать по мере готовности.

## Первый запуск после принятия приглашения

```sh
git clone https://github.com/aibarC/QULAQ-AI.git
cd QULAQ-AI
git config --local pull.ff only
git config --local fetch.prune true
git switch -c codex/frontend-shell
```

Для backend использовать имя вида codex/backend-evaluation. Настройки --local действуют только в этой копии; каждый участник выполняет их сам. Имя и email коммитов должны принадлежать самому участнику; не копировать чужую identity.

## Рабочий цикл

1. Проверить `git status`, текущую ветку и `git remote -v`. Не начинать синхронизацию поверх несохранённой чужой работы.
2. Сохранить свою работу понятным коммитом либо договориться о её сохранении; не выполнять автоматический stash/reset для очистки дерева.
3. Получить актуальные ссылки: `git fetch origin`.
4. Для новой задачи перейти на чистую main, выполнить `git pull --ff-only`, создать отдельную ветку.
5. Редактировать свою зону, проверить изменения соразмерно задаче, просмотреть diff. Добавлять в коммит конкретные нужные файлы.
6. Перед отправкой проверить `git diff --check` и статус. Если main изменился и это затрагивает задачу, на чистой рабочей ветке выполнить `git merge origin/main`, разрешить конфликты и повторить необходимые проверки.
7. Отправить только свою ветку: `git push -u origin <имя-ветки>`.
8. Открыть pull request в main. Указать, что изменилось, как проверено, какие новые поля/API или зависимости нужны второй стороне.
9. Другой участник проверяет затронутые общие интерфейсы. aibarC координирует слияния в main; основной способ — squash merge. После squash создавать новую ветку от обновлённой main, а не продолжать старую слитую ветку.

Первоначальная загрузка документов в main выполняется владельцем один раз. Дальнейшая работа — через ветки и PR. Если потребуются исключения, их явно согласовывают, а не обходят конфликты force push.

## При конфликте или отклонённом push

- Остановиться, выполнить fetch, посмотреть расхождение истории и изменения.
- В общую опубликованную историю не применять rebase/force push. Для синхронизации своей опубликованной ветки использовать merge после проверки чистоты дерева.
- Не делать reset --hard, git clean, автоматический выбор ours/theirs для всех файлов или удаление чужой ветки.
- Если в вашей ветке появились чужие коммиты — сначала понять их назначение и сохранить обе стороны.
- Не переписывать код напарника, чтобы временно скрыть ошибку интеграции. Обсудить формат и сделать минимальную совместимую правку.

## Данные и секреты

- API-ключи, .env, подписанная ссылка организаторов, реальные разговоры и аудио не коммитятся.
- .env.example может содержать только имена настроек и безопасные заглушки.
- Локальный набор хранить в .local/ или data/private/, исключённых из Git. В публичные fixtures включать только искусственные примеры.
- Не выводить секреты в логи и сообщения PR. Приватность репозитория не заменяет эти правила.

## Доступ и защита

bagdaulet-dev получает доступ Write (push). Приглашение требуется принять со своего GitHub-аккаунта. Переключение ролей приложения не связано с доступом к GitHub.

Правило PR/main действует как соглашение команды независимо от тарифных ограничений GitHub. Техническую защиту ветки следует проверять в настройках репозитория; этот документ сам её не включает.

По текущему запросу репозиторий приватный. ТЗ хакатона требует открытый репозиторий к сдаче: перед сдачей нужно отдельно согласовать публикацию и проверить содержимое. Автоматически делать репозиторий публичным не следует.
