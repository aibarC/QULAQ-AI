## Продукт: согласованная основа

Получаем **готовые транскрипты** через API организаторов. STT не требуется. DEV: 65 разговоров, 60 чатов и 5 звонков; RU35/KZ15/EN15. Поля: conversation_id, channel, language, transcript (timestamp/speaker/text), audio_url. Имена сотрудников не предоставлены, не выдумывать.

Две функциональные роли: пользователь (выбранный сценарий — специалист QA) и проверяющий апелляции. Оператор в записи — объект оценки, не обязательный аккаунт. В демо достаточно переключателя ролей.

Пользователь: Диалоги / Чек-листы / Мои апелляции. Проверяющий: Апелляции с доступом к полному разговору внутри обращения.

Путь: импорт набора → список → открыть разговор → выбрать чек-лист → оценить → JSON по критериям + доказательства → валидация и расчёт кодом → сохранённый результат. Можно оспорить критерий: комментарий → очередь проверяющего → человек подтверждает или меняет допустимое значение с причиной → код пересчитывает итог, сохраняя исходную оценку. Комментарий сам по себе не запускает ИИ. Запись из списка не исчезает.

Чек-лист редактируемый: критерии, веса, шкалы, условия N/A. Изменение правил создаёт новую версию оценки; изменение только весов можно пересчитать без LLM. Фиксированная схема c1–c8 в экспериментальном промпте — только benchmark, для приложения её нужно генерировать из конфигурации.

**Auto Improve AI — дополнительная функция, не MVP:** подтверждённая ошибка → предложение обобщённого правила/примера → отдельное одобрение человеком → версия контекста будущих оценок. Это не обучение весов. Не переносить непроверенные комментарии автоматически в system prompt.

## Чек-лист и расчёт

| ID | Критерий | Допустимые значения | Вес |
|---|---|---|---|
| c1 | Приветствие на языке клиента и представление в первом ответе | Да/Нет | 10 |
| c2 | Учитывает известные детали и уточняет недостающее | Да/Нет/N/A | 15 |
| c3 | Идентификация до закрытых данных/защищённого действия | Да/Нет/N/A | 20 |
| c4 | Корректная и полная консультация | 0/5/10/15/20/N/A | 20 |
| c5 | Вежливость и реакция на конкретное недовольство/неудобство | Да/Нет | 15 |
| c6 | Ясность и порядок общения, предупреждение об ожидании | 0/4/7/10 | 15 |
| c7 | (Итог ИЛИ дальнейшая помощь) И прощание | Да/Нет/N/A | 5 |
| c8 | Оскорбление, платная услуга в обход компании, раскрытие конфиденциального | Да/Нет | отдельно |

N/A: c2 — данных хватало с начала работы оператора, включая бот-контекст; c3 — идентификация не требовалась; c4 — чат закончился до сформулированного запроса; c7 — обрыв до возможности завершить. N/A не означает неуверенность или отсутствие нужного действия.

c4:20 всё существенное закрыто или дан корректный следующий шаг;15 пропущена второстепенная деталь;10 существенная часть не закрыта;5 общая непригодная для действия подсказка;0 нет ответа по существу/ключевая рекомендация ошибочна. c6:4 клиент вынужден переспрашивать из-за формулировок/порядка;7 иной заметный сбой;10 ясность;0 непонятный ход разговора.

Итог =100 × сумма(вес × значение/максимум) / сумма применимых весов. Boolean Да=1, Нет=0. N/A исключается. c8 не обнуляет итог. Decimal HALF_UP до2знаков — выбранная реализация округления, не явно заданное правило PDF. Порог первой реакции3минуты, теги и вложения исключены.

1. Уточнить оставшееся время до сдачи (пользователь ещё не ответил) и проверить доступные GPU/квоту в аккаунте Kaggle либо Colab. Аккаунт в этой сессии не открывали, сервер не выделяли, деньги не тратили на обучение.

3. Подготовить надёжные цели: разговор + **текущая формулировка критерия/чек-листа** → значение/применимость + краткое основание + evidence. Обучение должно сохранять способность учитывать изменяемые правила, а не запоминать фиксированные c1–c8.
4. Разобрать спорные границы с человеческим проверяющим; не объявлять AI-консенсус официальной истиной. Синтетические примеры и черновые ответы Kimi допустимы после проверки.
5. Разделять train/validation/test по исходным разговорам и близким/переведённым шаблонам ДО генерации производных примеров. Нельзя строки одного разговора разнести в train/test и получить искусственный успех. Ранее открытый holdout уже использован для анализа: не выдавать будущую подгонку по нему за новый независимый тест.
6. Подготовить notebook QLoRA, сделать пробный шаг обучения и проверить память/длину. Сохранять адаптеры, tokenizer, параметры и checkpoints вне временной сессии облака. Реальные данные не публиковать как public dataset/notebook.
7. Сравнить исходную модель, её обученную версию и Kimi на одинаковом отдельном наборе RU/KZ/EN. Метрики: Нет↔N/A, оценки по каждому критерию, evidence, пропуск грубых нарушений, валидность ответа, повторяемость, latency и ресурсы. Общий балл может скрывать противоположные ошибки.
8. Если улучшения нет или есть регрессия — сообщить и сохранить baseline. Не считать сам факт fine-tuning достижением качества.

Дообучение ещё не разрешает проблему дальнейшего размещения: отдельно выбрать, где модель будет обслуживать UI после завершения notebook. Не обещать постоянный production API из бесплатной временной сессии.
